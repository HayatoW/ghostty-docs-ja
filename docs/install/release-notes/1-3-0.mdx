Ghostty 1.3.0 は、スクロールバック検索、ネイティブのスクロールバー、
シェルプロンプト内でのクリックによるカーソル移動など、特に要望の多かった
機能を多数盛り込んだ大規模なリリースです。全プラットフォームを対象とした数百件の
改善、バグ修正、パフォーマンスの最適化も含まれています。

このリリースには、**180 人のコントリビューター**による**6 か月分の作業**が
**2,858 件のコミット**として含まれています。リリースの実現に力を貸してくださった
コントリビューター、メンテナー、コミュニティのモデレーター、翻訳者、
パッケージ作成者、ユーザーの皆さんに感謝します。

変更履歴の全文も含め、このリリースノートは Ghostty のメンテナーが人の手で、
丹精を込めて書き上げました。執筆には延べ 16 時間以上かかっています。
どうぞお楽しみください。🥰

### スクロールバック検索 {/* #scrollback-search */}

関連 PR: GH-9585 GH-9602 GH-9687 GH-9702 GH-9709 GH-9756

macOS では `cmd+f`、GTK では `ctrl+shift+f` で、ターミナルのスクロールバックを
検索できるようになりました。ビューポート内の一致箇所がすべて強調表示され、
矢印ボタンのほか、macOS では `cmd+g` / `shift+cmd+g`、GTK では
`enter` / `shift+enter` で一致箇所を移動できます。もちろん、これらの
キーバインドはすべて変更できます。

`Find Previous` のショートカット、システムの検索用ペーストボードが

検索には専用スレッドを使っており、ターミナルの I/O と並行して動作します。
短時間ずつターミナルのロックを取得して検索を進めるため、I/O のスループットや
描画への影響を最小限に抑えられます。検索を使わない場合や検索バーを
閉じた場合には、検索スレッドは終了し、リソースを消費しません。

### シェルプロンプト内でのクリックによるカーソル移動 {/* #click-to-move-cursor-in-shell-prompts */}

関連 PR: GH-10455

Ghostty は [`click-events`](https://sw.kovidgoyal.net/kitty/shell-integration/#notes-for-shell-developers)
と [`cl=line`](https://gitlab.freedesktop.org/Per_Bothner/specifications/blob/master/proposals/semantic-prompts.md)
という [OSC 133 セマンティックプロンプト仕様](https://gitlab.freedesktop.org/Per_Bothner/specifications/blob/master/proposals/semantic-prompts.md)
の拡張に対応しました。通常のテキストフィールドと同じように、入力中の
シェルプロンプト内をマウスでクリックしてカーソルを移動できます。

<Video src="https://web.files.ghostty.org/release-notes-1-3-0-click.mp4" />

Fish (4.1 以降) と Nushell (0.111 以降) は、この機能に標準で対応しています。
ほかのシェルでは、Ghostty が注入するシェル統合によって対応状況が異なります。
対応するシェルなら、特別な操作をしなくても使えます。

さらに、Ghostty の OSC 133 実装が従来よりも完全で正確になり、以前から対応していた
プロンプトへの移動やコマンド出力のコピーがより正確に動作します。プロンプトが
入力待ちのときにサイズを変更した場合の動作も改善しています。

ちょっと面白い点として、OSC 133 の領域を可視化するデバッグ用の
オーバーレイも追加しました。この機能への対応を進めるシェル開発者にとって、
大きな助けになりました。ターミナルインスペクターで誰でも有効にできます。

### コマンドの終了通知 {/* #command-finished-notifications */}

関連 PR: GH-8992 GH-10934

長時間実行されていたコマンドが終了したときに、Ghostty から通知を受け取れるように
なりました。たとえば、ビルドや一連のテストを開始してから別のウィンドウに
切り替え、完了を知りたいときに便利です。

この機能は、次の 3 つの新しい設定で制御します。

```
notify-on-command-finish = unfocused
notify-on-command-finish-action = no-bell,notify
notify-on-command-finish-after = 30s
```

`notify-on-command-finish` は通知のタイミングを制御します。`never`（デフォルト）、
`unfocused`（ターミナルにフォーカスがないときのみ）、`always` から選べます。
`notify-on-command-finish-action` は通知の方法を制御します。`bell`（デフォルト）と
`notify`（デスクトップ通知）に対応し、組み合わせや無効化もできます
（例: `no-bell,notify`）。
`notify-on-command-finish-after` は通知を送るまでのコマンドの最短実行時間を設定し、
デフォルトは 5 秒です。

この機能は OSC 133 エスケープシーケンスでコマンドの実行を追跡するため、
シェル統合を有効にするか、Fish や Nushell のように OSC 133 シーケンスを
標準で送信するシェルを使う必要があります。

### キーテーブル、キーバインドの連鎖、`catch_all` {/* #key-tables-chained-keybinds-and-catch_all */}

関連 PR: GH-9984 GH-9961 GH-9977 GH-10098

Ghostty 1.3 では、キーバインドを使いこなしたい方向けに、キーテーブル、
キーバインドの連鎖、特殊キー `catch_all` などの新機能を追加しました。

**キーテーブル**により、tmux のようにモードを切り替えながらキーバインドを
使えます。キーテーブルは、必要に応じて有効化・無効化できる、名前付きの
キーバインドの集まりです。テーブルが有効な間は、そのテーブル内から
キー入力に対応する設定を最初に探すため、完全に独立したモードを作成できます。

テーブルを定義するには、既存の `keybind` 設定で `<name>/<binding>` の
書式を使います。たとえば、次のように記述します。

```
keybind = resize/arrow_up=resize_split:up,10
keybind = resize/arrow_down=resize_split:down,10
keybind = resize/arrow_left=resize_split:left,10
keybind = resize/arrow_right=resize_split:right,10
keybind = resize/escape=deactivate_key_table
keybind = resize/catch_all=ignore

keybind = ctrl+a=activate_key_table:resize
```

この例では、`ctrl+a` を押すと `resize` テーブルが有効になります。有効な間は、
矢印キーで分割のサイズを変更でき、ほかのキーはすべて無視されます。
`escape` を押すとテーブルが無効になり、通常のキーバインドに戻ります。

macOS と GTK の両方で、既存のキーシーケンスの表示と同様、キーテーブルが
有効なときに専用の UI インジケーターが表示されます。

<p align="center">
  <a href="/images/1-3-0/key-overlay.png" target="_blank">
    <img
      src="/images/1-3-0/key-overlay.png"
      style={{ maxWidth: "85%", margin: "10px" }}
    />
  </a>
</p>

**キーバインドの連鎖**を使うと、ひとつのキーに複数のアクションを割り当てられます。
`chain` キーを使って、直前に定義したキーバインドにアクションを追加します。

```
keybind = ctrl+shift+f=toggle_fullscreen
keybind = chain=toggle_window_decorations
```

これにより、`ctrl+shift+f` を押すと両方のアクションが実行されます。
連鎖は、キーテーブル内でもキーシーケンスでも使えます。

**`catch_all`** は、明示的に割り当てられていないあらゆるキーに一致する新しい特殊キーです。
修飾キーと組み合わせたり（`ctrl+catch_all=ignore`）、キーシーケンスの中で
使ったり（`ctrl+a>catch_all=end_key_sequence`）できます。意図しない入力を
ターミナルに渡さず、そのモード内で完結するキーバインドの集まりを簡単に作れます。

### 作業ディレクトリの継承を細かく制御 {/* #fine-grained-working-directory-inheritance-controls */}

関連 PR: GH-9158

新しい `tab-inherit-working-directory` と `split-inherit-working-directory` の
設定で、新しいタブ、ウィンドウ、分割ペインで作業ディレクトリを継承するかを
個別に制御できます。設定に関する要望の中でも特に多かったもののひとつです。

ただしこの用途への要望が非常に多かったため、早く使えるように、
当面は用途を絞った設定を追加しました。

### パフォーマンスの改善 {/* #performance-improvements */}

関連 PR: GH-9662 GH-9645

[asciinema](https://asciinema.org/) の協力により、Ghostty のパフォーマンスの
分析と最適化に使える、約 4 GB の公開ターミナル録画データを受け取りました。
合成ワークロードだけでなく、実際のターミナルの利用に基づくデータを使えるのは
ありがたいことです。

このデータで I/O 処理を大幅に改善し、Ghostty がデータセット全体を再生する時間を
数分から数十秒に短縮できました（もちろん、asciinema はすべての待ち時間を
無視するように設定しています）。Alacritty の vtebench など、合成ベンチマークでも
改善が見られました。

I/O の更新に加えてレンダラーの設計も見直し、レンダラーがターミナルのロックを
保持する時間を **2 分の 1～5 分の 1** に短縮しました。さらに、変更や再描画が
必要な領域の追跡を改善したことで、ほとんどのフレームではロック自体を保持しません。
この改善は Metal と OpenGL の両方に適用されます。

### 安定性の改善 {/* #stability-improvements */}

関連 PR: GH-10337 GH-10401 GH-11089 GH-11109 GH-9594

Ghostty 1.3 では、安定性と堅牢性の向上に大きく力を入れました。

以前の Ghostty で Claude Code が頻繁に引き起こしていた、大規模なメモリリークを
このリリースで修正しました。このリークは Ghostty 1.0 から存在していましたが、
発生させるのが難しく、まれにしか起きませんでした。ところが、Claude Code が
リークの発生に必要な条件をすべて満たすようになり、多数の利用者がいることもあって、
広く発生するようになりました。リークと修正の詳細は、
[この件を取り上げたブログ記事](https://mitchellh.com/writing/ghostty-memory-leak-fix)をご覧ください。

また、このリリースでは [AFL++](https://aflplus.plus/) を使い、Ghostty の
ターミナルエスケープシーケンスパーサー（GH-11089）と VT ストリームプロセッサー全体
（GH-11109）を対象に、広範なファジングを行いました。この過程で、クラッシュや
潜在的なメモリ安全性の問題を 10 件ほど見つけて修正しました。実際の利用で
問題になった例は確認されていませんが、起きていても不思議ではありません。
長期的には、Ghostty を継続的にファジングするための基盤を整えたいと考えています。

すべての `try` 箇所に障害を注入して、`errdefer` によるクリーンアップ経路を
体系的にテストする、新しいテストツール [Tripwire](https://mitchellh.com/writing/tripwire)
（GH-10401）を開発しました。このテストで、フォントサブシステムのメモリリーク、
状態の破損、グリフキャッシュの破損など、複数のバグを発見して修正しました。
対象はエラーからの復旧経路のバグに限られますが、メモリ不足や GPU ドライバーの
不具合など、予期しないエラーに対して Ghostty がより堅牢になります。

メモリについても数か所を最適化しました。代替画面用のメモリは必要になってから
割り当てるため、これを使用しないセッションではターミナルあたり数 MB を
節約できます（GH-9594）。ほかにも、すべてのサブシステムにさまざまな小さな
改善が入っています。

### AppleScript (macOS) {/* #applescript-(macos) */}

関連 PR: GH-11208 GH-11251

Ghostty の macOS 版は AppleScript に標準対応し、強力な自動化や連携が可能に
なりました。AppleScript では、ウィンドウ、タブ、分割、個々のターミナルの
状態を調べたり、制御したりできます。作成や移動といった基本操作のほかに、
テキスト、キー、マウスの入力も送信できます。

スクリプトを使うことで、ターミナルのレイアウトを自動で作成したり、
コマンドを複数のターミナルへ一斉送信したり、作業ディレクトリで指定して
ターミナルへ移動したりできます。

次は、最前面の Ghostty ウィンドウで現在フォーカスされているターミナルを
対象にした短い例です。

```AppleScript
tell application "Ghostty"
    set term to focused terminal of selected tab of front window
    input text "pwd\n" to term
end tell
```

AppleScript はデフォルトで有効で、macOS のオートメーション権限（TCC）で
保護されています。別のアプリが Ghostty を制御する前には、macOS が
許可を求めます。AppleScript のサポートが不要なら、
`macos-applescript = false` を設定してください。

<Important>
  これは **1.3 のプレビュー機能**として提供します。AppleScript の機能は、
  ほかの機能ほどプレリリースビルドでのテスト期間を取れませんでした。
  ユーザーからのフィードバックを受けて、1.4 では互換性を壊す API の変更や、
  大きな新機能の追加を行う見込みです。
</Important>

### 分割のドラッグ＆ドロップ (macOS) {/* #split-drag-and-drop-(macos) */}

関連 PR: GH-10090

macOS で分割をドラッグして並べ替えられるようになりました。分割の上端付近に
マウスを合わせるとハンドルが表示され、別の分割位置へドラッグできます。
ハンドルをつかみ、移動先にドロップするだけで、ターミナルの内容、
作業ディレクトリ、実行中のプロセスがすべて一緒に移動します。

<Video src="https://web.files.ghostty.org/release-notes-1-3-0-split-drag.mp4" />

分割をウィンドウの外や新しいタブへドラッグすることもできます。
これらの操作は取り消し・やり直しに対応しているため、間違った場所に
ドロップしても簡単に元に戻せます。

分割を閉じて作り直さなくても、マウスでターミナルのレイアウトを変更できます。
この実装は、分割を新しいタブやウィンドウにドラッグする機能など、
将来の拡張の土台にもなります。

GTK 版での実装は今後のリリースで予定しています。

## システム要件 {/* #system-requirements */}

Ghostty 1.2 からシステム要件に変更はありません。

**macOS:** Ghostty 1.3 が必要とする最小 macOS バージョンは、
macOS 13 Ventura のままです。

**GTK:** Ghostty 1.3 には **GTK 4.14** と **libadwaita 1.5** が必要です。
これは、[GTK/Adwaita のバージョン方針](/docs/linux/#supported-gtkadwaita-versions)に
沿った要件です。GTK や Adwaita のバージョンが古いシステムでは、Ghostty の
旧バージョンを使うか、コミュニティが管理する Snap または Flatpak パッケージを
使うことで、この要件を回避できます。

<Important>
  **macOS 13 をサポートする最後のバージョンです。** Ghostty 1.4 以降
  （および 1.4 に先立つ tip リリース）では、macOS 14 が最低要件になります。
  Apple は 2025 年秋に macOS 13 のセキュリティサポートを終了しており、
  この変更は Apple の通常のサポート方針に沿ったものです。
</Important>

## 互換性を壊す変更 {/* #breaking-changes */}

1.3.0 では、次のデフォルトの動作が変わりました。

- クリップボードにコピーするときのデフォルト形式が `text` から `mixed` に
  変わりました。`mixed` 形式では、プレーンテキストと HTML の両方を
  クリップボードに設定します。問題が起きる場合は、形式を明示して
  `copy_to_clipboard` を割り当て直してください。GH-9418
- GTK: FreeType のデフォルトが、ほかの大半の GTK アプリケーションに合わせて
  フルヒンティングからライトヒンティングに変わりました。`freetype-load-flags`
  の設定で以前の動作に戻せます。GH-9253

## Libghostty {/* #libghostty */}

Ghostty 1.3 のリリースに直接関係する話ではありませんが、1.3 の開発サイクルの
目標のひとつは、[libghostty](https://mitchellh.com/writing/libghostty-is-coming) に
本格的に注力し始めることでした。ここで進捗をお伝えします。

1.3 の開発サイクル中に libghostty の切り出しに成功し、独立した Zig モジュールとして
利用できるようになりました。この Zig モジュールは機能がそろっており、コードの
ほとんどを Ghostty と共有しています。同時に、
[開発中の C API](https://libghostty.tip.ghostty.org/index.html) も公開しています。
Ghostty のリポジトリには
[Zig と C のサンプル集](https://github.com/ghostty-org/ghostty/tree/main/example)があります。

どちらのモジュールも、バージョン付きリリースのタグを付けられる段階には
まだ達していません。それでも、無償・商用を問わず数十のプロジェクトが
[すでに libghostty を使っており](https://github.com/Uzaaft/awesome-libghostty)、うれしく思います。
興味がある方は、Discord の libghostty チャンネルにお越しください。

Ghostty の開発チームは、Ghostty の GUI と libghostty のリリースサイクルを分けることに
しました。libghostty は、Ghostty のデスクトップアプリケーションとは独立した
バージョンとリリース日程を持つことになります。利用者層も安定性の要件も異なる
ライブラリとデスクトップアプリケーションを、それぞれに適した速度で開発できます。

libghostty の初回リリースにいつタグを付けられるかはまだわかりませんが、
Zig モジュールと C API の両方で開発を進めており、近いうちにリリースしたいと考えています。

## 財務状況の報告 {/* #financial-update */}

Ghostty は 1.3 の開発サイクル中に、正式に[非営利プロジェクト](/docs/sponsor)になりました。

この変更が重要なのは、商業的利益のために Ghostty が売却されたり、方針を転換されたり、
別の用途に転用されたりしないことを、実効性のある形で保証できるからです。非営利の
組織形態は、Ghostty を導入し貢献する個人やコミュニティを守り、私的な利益より
公益を優先する、使命に沿った組織がプロジェクトを運営することを保証します。
この決定の背景については、[当初の発表](https://mitchellh.com/writing/ghostty-non-profit)をご覧ください。

プロジェクトに関わり、継続的に質の高い成果を残してきた方々に報酬を支払うため、
**5 件のコントリビューター契約**を正式に結びました。契約の対象はコミュニティの管理、
グラフィックス、Unicode 互換性、GTK、Discord と GitHub の連携です。
報酬の対象となる作業は合わせて約 300 時間で、コントリビューターが Ghostty での活動を
有償で続けられる機会を提供できることをうれしく思います。

Ghostty を支援したい方は、[スポンサーシップのページ](/docs/sponsor)をご覧ください。

## ロードマップ {/* #roadmap */}

要望の多かったスクロールバック検索やネイティブのスクロールバーが実装された今、
Ghostty 1.3 は、Ghostty を
[「現存する最高のターミナルエミュレーター」](https://mitchellh.com/writing/ghostty-1-0-reflection)
にするという長年の目標を実現した、素晴らしいリリースだと思います。

もちろん「最高」は主観ですが、重要なのは、Ghostty 1.3 が実績のあるターミナル
エミュレーターに期待される主要機能をすべて備え、高い完成度とパフォーマンスで
提供していることです。もちろん今後も Ghostty の改善を続けますが、プロジェクトの
開発における大きな節目です。

当面は [libghostty](https://mitchellh.com/writing/libghostty-is-coming) の安定化と、
リリースタグの付与に注力します。数十のプロジェクトが
[すでに libghostty を使っており](https://github.com/Uzaaft/awesome-libghostty)、
いずれは Ghostty のデスクトップアプリケーション自体より広く利用され、
影響力を持つようになると考えています。プロジェクトにとって重要な次の一歩です。

企業向けのスポンサーシップ制度の整備、スポンサーへのより具体的な特典の提供、
Ghostty が資金をどのように活用しているかの広報など、非営利プロジェクトとして
進めるべきことも数多くあります。

Ghostty 1.4 では、デスクトップアプリケーションの改良を続けます。
特定の機能を約束するつもりはありませんが、Ghostty のスクリプト操作、本格的な
Tmux 制御モード、グラフィカルな設定画面などに力を入れています。

よくいただく要望にお答えすると、**Microsoft Windows** 対応はまだ予定していません。
長期ロードマップには引き続き含まれていますが、高機能で強力な libghostty に注力する
ことが、長い目で見てより良い Windows 対応につながると考えています。
libghostty 自体はすでに Windows に対応しています。

Ghostty 1.4 は 6 か月のリリースサイクルを継続し、9 月を予定しています。
より頻繁な更新を希望する方には、macOS では
[`tip` リリースチャンネル](/docs/config/reference#auto-update-channel)を使い、
Linux では頻繁に[ソースからビルド](/docs/install/build)することをおすすめします。
