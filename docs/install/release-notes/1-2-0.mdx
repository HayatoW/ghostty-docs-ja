Ghostty 1.2.0 には、**149 人の貢献者**による **2,676 件のコミット**にわたる、**6 か月分の成果**が詰まっています。このリリースを支えてくださった貢献者、メンテナー、コミュニティのモデレーター、翻訳者、パッケージ作成者、ユーザーの皆さんに感謝します。このリリースでは Ghostty のあらゆる部分が大きく改善され、数百件のバグが修正されています。

## セキュリティ {/* #security */}

- macOS: [GHSA-q9fg-cpmh-c78x](https://github.com/ghostty-org/ghostty/security/advisories/GHSA-q9fg-cpmh-c78x)。脆弱性のある別のソフトウェアや悪意のあるソフトウェアが、Ghostty を権限昇格の経路として利用できる問題を修正しました。一連の動作が始まるには、Ghostty 以外に脆弱性のあるアプリが必要です。そのため、このアドバイザリのリスクは低いと判断しています。

### クイックターミナルのサイズ {/* #quick-terminal-size */}

PRs: GH-2384

新しい `quick-terminal-size` 設定で、クイックターミナルの既定のサイズを指定できるようになりました。これは特に要望の多かった機能の一つです。

`quick-terminal-size` 設定では、パーセントとピクセルの両方でサイズを指定できます。値を一つだけ指定すると、配置に応じた主軸のサイズになります。二つ指定すると、二つ目の値は副軸のサイズになります。以下は指定例です。

```
# Percentage, primary axis only
quick-terminal-size = 25%

# Pixels work too, primary axis only
quick-terminal-size = 600px

# Two values specify primary and secondary axis
quick-terminal-size = 25%,75%

# You can also mix units
quick-terminal-size = 300px,80%
```

*主軸*は `quick-terminal-position` 設定で決まります。`top` と `bottom` では高さ、`left` と `right` では幅が主軸です。`center` の場合はモニターの向きによって異なり、横向きなら高さ、縦向きなら幅です。

サイズを設定できるだけでなく、実行中にクイックターミナルのサイズを変更でき、Ghostty が動作している間はそのサイズが保持されます。以前はサイズが固定されており、モニターの大きさや解像度によっては使いづらいことがありました。

### SSH の改善（開発中） {/* #ssh-improvements-(work-in-progress) */}

PR: GH-7608

Ghostty に、[Ghostty の terminfo](/docs/help/terminfo) にまだ対応していないリモートマシンとの SSH 接続の互換性を高める、オプトインのシェル統合機能が追加されました。

新しいオプトイン機能 `ssh-env` は、SSH セッションの `TERM` 変数を自動的に `xterm-256color` に設定します（セッションがよりうまく動作するよう、ほかの環境変数もいくつか転送します）。厳密には正しい設定ではなく応急処置ですが、ほとんどの場合は欠点よりも利点のほうが上回ります。

新しいオプトイン機能 `ssh-terminfo` は Ghostty の terminfo をリモートマシンへ自動でコピーします。これにより、`TERM` に正しい `xterm-ghostty` を設定でき、リモート側のプログラムが Ghostty の機能をすべて活用できます（Ghostty が対応していない xterm の機能も避けられます）。

どちらの機能もシェルの `ssh` コマンドを上書きする必要があるため、オプトインです。この操作にはリスクが伴うので、何を変更するのかを利用者に理解しておいてほしいと考えています。安定して動作するよう最善を尽くしていますが、想定しきれない例外もあります。そのため、まだ開発中の機能としてフィードバックを募集しています。

### レンダラーの再設計 {/* #renderer-rework */}

PRs: GH-7620

レンダラーのバックエンドを再設計し、OpenGL と Metal のどちらで描画する場合も中核のロジックを共有するようにしました。今後この部分をよりすばやく改善できるほか、両バックエンドの機能を揃えやすくなります。Metal にのみ実装され、OpenGL にはない機能が多く、差が問題になり始めていました。

この再設計に伴い、OpenGL バックエンドにもいくつかの改善を加えました。処理効率が向上し、機能面でも Metal バックエンドとほぼ同等になっています。

これにより Linux でも正しく線形アルファブレンディングが行われるようになり、背景色と前景色の特定の組み合わせで文字の輪郭に生じていた描画の乱れが解消されます。Linux での `alpha-blending` 設定の既定値は `linear-corrected` になりました。線形ブレンディングを行いつつ、文字の見かけの太さが従来の非線形ブレンディングと同じになるよう補正します。

この再設計により、カスタムシェーダーも実行中に再読み込みできるようになりました。

### グラフィカルな進捗バー {/* #graphical-progress-bars */}

PRs: GH-7975, GH-8477

Ghostty は [ConEmu の `OSC 9;4` シーケンス](https://conemu.github.io/en/AnsiEscapeCodes.html#ConEmu_specific_OSC) を認識し、GUI ネイティブの進捗バーを表示するようになりました。

私たちの知る限り、Ghostty はこの機能に対応した最初の macOS 向けターミナルエミュレーターです。Linux と Windows では、Ghostty 以外にも複数のターミナルがすでに対応しています。

進捗バーには、成功やエラーの状態、完了までの進捗値、進捗量が不明な場合の表示（脈動するアニメーション）などを表示できます。以下に示すように、[Amp](https://ampcode.com/) などのプログラムはすでに進捗バーで動作状況を表示しています。

<Video src="https://web.files.ghostty.org/release-notes-1-2-0-progress.mp4" />

グラフィカルな進捗バーには、Windows、Linux、macOS の複数のターミナルに加え、systemd や Zig の CLI といった主要なターミナルプログラムの一部も対応しています。対応するターミナルの増加に伴い、この機能を使うプログラムが増えることを期待しています。

現在の Ghostty では、ターミナルの上端にシンプルな進捗バーを表示します。今後はタブのヘッダー、タスクバー、Dock アイコンなどにも進捗を表示できるようにする予定です。

<Note>
  進捗を報告する `OSC 9;4` シーケンスは、iTerm2 の通知シーケンスと競合します。Ghostty は両方のシーケンスに対応する唯一のエミュレーターです。競合を解消するため、`OSC 9;4` は常に進捗報告として解釈します。つまり、`;4` で始まる通知は通知として送れません。該当する通知文がごく限られており、より推奨される `OSC 777` 通知シーケンスの対応も広がっていることから、妥当な妥協点と考えています。
</Note>

### 組み込みの Nerd Font の改善 {/* #built-in-nerd-font-improvement */}

PR: GH-7809、および軽微な問題を修正する後続の PR

組み込みの Nerd Font の記号は、JetBrains Mono の Regular、Bold、Italic、Bold Italic にパッチを適用して提供するのではなく、記号専用の独立したフォントで提供するようになりました。組み込みの JetBrains Mono も、4 つの静的フォントに代わってバリアブルフォントを使います。これにより、Ghostty に埋め込むフォントの容量が大幅に減りました。

これに伴い、より新しい版の Nerd Fonts の記号を採用しました。新しく追加された記号も正しく描画されます。

大きな変更は、公式の Nerd Fonts パッチャーと同様に、Ghostty が Nerd Fonts の記号をセルのサイズに合わせて自動で拡大・縮小するようになったことです。これにより、パッチを適用していない普通のフォントでも、以前パッチ済みのフォントを使ったときとほぼ同じか、まったく同じ表示になります。

Powerline などのグリフはいずれの場合もセルに合ったサイズになるため、Ghostty ではもはやパッチ済みのフォントを _使う必要がありません_。

### キーバインドの再設計 {/* #key-binding-rework */}

PR: GH-7320

[W3C のキーイベントコード仕様](https://www.w3.org/TR/uievents-code/) に基づき、キーバインドの動作を一貫させるように見直しました。OS やキーボード配列が異なっても予測しやすく、正しく動作するようになりますが、**既存のキーバインドが動かなくなる可能性がある大きな挙動の変更**も含まれます。

単一のコードポイントで表される文字はすべて、キーボード配列で入力される文字に一致します（配列に依存します）。たとえば `ctrl+c` は、US 標準キーボードで US 配列を使っていれば物理的な「c」キーに、Dvorak 配列なら「i」キーに一致します。英語圏以外で使われる文字も同様です。コードポイントは大文字・小文字を区別せず、Unicode のケースフォールディングで照合します（Windows と macOS もキーボードショートカットを同様に扱います）。

それ以外のキー名はすべて物理キーに対応し、W3C のキーコードに従って命名されます。たとえば `ctrl+KeyA` は常に US 物理配列の「a」キーに一致します（`KeyA` が US キーボードを基準とするのは、Ghostty 独自の判断ではなく仕様です）。ここでいう「物理」とは、OS や GUI フレームワークが送るキーコードを指します。キーを「ハードウェア」レベルで再割り当てするツールで上書きできる場合が多くありますが、ソフトウェア側のキーボード配列では上書きされません。

この変更に伴い、**`physical:` プレフィックスを削除しました。** 上述のとおり、物理キーのキーバインドは複数のコードポイントからなるキー名で明示します。従来の `physical:` 付きキーバインドは引き続き動作しますが、新しい形式に移行してください。

後方互換性のため、W3C に準拠していなかった Ghostty の既存のキー名は、すべて対応する W3C の名前に変換されます。たとえば、`grave_accent` は `backquote` になります。

### ターミナルベル {/* #terminal-bell */}

PRs: GH-7099, GH-5326, GH-7087, GH-7101, GH-7118, GH-7148, GH-7842, GH-7533

macOS と GTK の両方で、Ghostty がターミナルベル（ASCII の `BEL`、または `0x07`）に対応しました。ベルが鳴ったときの挙動は `bell-features` 設定でカスタマイズできます。既定値は便利さを損なわない範囲で控えめにしており、より目立つ機能は `bell-features` で任意に有効化できます。

macOS の既定の挙動では、ターミナルのタイトルにベルの絵文字（🔔）を表示し、Dock アイコンを一度跳ねさせ、Dock とアプリケーションスイッチャーに表示される Ghostty アイコンにバッジを付けます。音は鳴りません。

GTK の既定の挙動では、ターミナルのタイトルにベルの絵文字（🔔）を表示し、ウィンドウが注意を求めていることを示すフラグを立てます。「注意を求めている」ウィンドウをどう扱うかは、ウィンドウマネージャーやデスクトップ環境によって異なります。音は鳴りません。

GTK は音を鳴らすベルにも対応していますが、既定では無効です。`bell-features=audio` で有効化できます。`bell-audio-path` 設定で再生する音を指定することもできます。`bell-features=system` 機能（既定では無効）は「システムのビープ音」を使います。通常はこれもシステム共通の設定で音を鳴らすようにできます。

GTK では、`bell-features=border` で境界線を点滅させるアニメーションも有効にできます。他のターミナルエミュレーターの「視覚ベル」に相当します。

将来の Ghostty では、macOS でもすべてのベル機能を使えるようにする予定です。

### ターミナルエミュレーションの互換性 {/* #terminal-emulation-compatibility */}

Ghostty 1.2 ではターミナルエミュレーションの中核に数十件の改善を加え、ターミナルプログラムが他のエミュレーターと同様に、Ghostty でも一貫して正しく動作するようにしました。関連する変更の全一覧は [ターミナルの機能](#terminal-capabilities) の節にあります。

改善は、ごく小さなもの（実際に使っているプログラムが確認されていないシーケンスへの対応、GH-7443）から、非常に重要なもの（実際のプログラムの一部が動かなくなる問題の修正、GH-8590）まで多岐にわたります。Ghostty ではターミナルエミュレーションの互換性を重視し、既存の幅広い機能に対応できるよう努めています。

正しく実装するのは簡単ではありません。ターミナルエミュレーションの機能で正式に仕様が定められているのはごく一部で、大半は既存のエミュレーターの挙動をもとにした事実上の標準に従っています。また、統一的な標準化団体が存在しないため、プロトコル同士がしばしば競合します。どちらを優先するか、またはどのように折り合いを付けて両方に対応するかを、私たちが判断する必要があります。

たとえば、[進捗バー](#graphical-progress-bars) のシーケンスは iTerm2 のデスクトップ通知シーケンスと競合します。妥協策として、進捗バーだと一意に判断できる場合は通知よりも優先します。そのため、本文が進捗バーを設定するシーケンスと完全に一致する通知は送れません。Ghostty はこの妥協策によって、進捗バーと iTerm2 のデスクトップ通知の両方を扱える数少ないターミナルの一つになっています。[^2]

### macOS: 閉じる操作の取り消しとやり直し {/* #macos:-undoredo-close */}

PRs: GH-7535

ターミナルを閉じるすべての操作を、標準の macOS キーバインド（`Cmd+Z` と `Cmd+Shift+Z`。割り当て変更可）で取り消したり、やり直したりできるようになりました。対象は、分割、タブ、ウィンドウ、すべてのウィンドウ、ほかのタブを閉じる操作などです。

取り消しとやり直しを可能にするために、閉じたばかりのターミナルは設定された時間（既定では 5 秒）のあいだ非表示のまま動作し続けます。この間に操作を取り消すと、ターミナルが元の場所に開きます。ターミナルは動作し続けていたので、閉じる前の状態がそのまま復元されます。

ターミナルを閉じる操作を取り消せる時間は、`undo-timeout` 設定で変更できます。

<Video src="https://web.files.ghostty.org/release-notes-1-2-0-undo.mp4" />

今後の Ghostty では、分割のサイズ変更やタブの移動など、取り消しとやり直しが可能な GUI 操作を増やす予定です。

### GTK: メモリリークを解消する全面的な書き直し {/* #gtk:-full-leak-free-rewrite */}

PR: GH-7961、[`gtk-ng` 関連の PR](https://github.com/ghostty-org/ghostty/pulls?page=4&q=is%3Apr+is%3Aclosed+gtk-ng)

[GObject の型システム](https://docs.gtk.org/gobject/concepts.html) を全面的に活用し、GTK アプリを一から書き直しました。その過程ですべての機能を [Valgrind](https://valgrind.org/) でテストし、メモリリーク、未定義のメモリアクセス、解放済みメモリの使用などを検査しました。

詳しい経緯は元の PR を参照してください。この書き直しで、GTK アプリは安定性が増して現代的になり、貢献者にとって保守しやすくなりました。

1.1.3 の GTK アプリには既知のメモリリークがいくつかあり、長時間使い続けると Ghostty の再起動が必要でした。多くの開発者はターミナルを普段から開きっぱなしにしており、そもそもアプリの再起動が必要になるべきではありません。現在の GTK アプリは安定しており、tip 版のユーザーからも、何週間も起動したままでも問題がなかったと報告されています。

この恩恵は GTK ユーザーだけのものではありません。この取り組みを機に、コミットごとに Ghostty の全単体テストを Valgrind で実行するようになりました（GH-8309）。単体テストの 90% 以上がクロスプラットフォームのコードを対象としており、Ghostty 全体の安定性と信頼性の向上につながります。

<Note>
  Valgrind がメモリの問題を検出できるのは、実行されたコードパスだけです。GUI のすべての操作は試しましたが、Ghostty のすべてのコードパスを実行したわけではありません。
</Note>

## システム要件 {/* #system-requirements */}

**macOS:** Ghostty 1.2 が必要とする最低バージョンは、引き続き macOS 13（Ventura）です。新たに macOS 26（Tahoe）にも対応しました。

**GTK:** Ghostty 1.2 には **GTK 4.14** と **libadwaita 1.5** が必要です。これは [GTK/Adwaita のバージョン方針](/docs/linux/#supported-gtkadwaita-versions) に沿っています。古い GTK や Adwaita を使っているシステムでは、古いバージョンの Ghostty や、コミュニティが管理する Snap または Flatpak パッケージを使うことで、この要件を回避できます。

## 互換性を損なう変更 {/* #breaking-changes */}

- GTK: libadwaita が必須になりました。1.1.0 のリリースノートで [この変更を予告しており](/docs/install/release-notes/1-1-0#gtk:-forcing-a-dependency-on-libadwaita)、その理由もリンク先に詳しく記載しています。ご意見を寄せる前に、ぜひ注意深くお読みください。コミュニティから意見を募り、この判断について時間をかけて議論しました。SSD 対応や CSS による本格的なスタイル設定など、寄せられた懸念に対処する機能もリリースしています。
- GTK: 必要な OpenGL の最低バージョンが 4.3 になりました。性能を向上させ、一部の描画バグを修正しやすくし、OpenGL バックエンドを保守しやすくするための変更です。OpenGL 4.3 が公開されたのは 2012 年なので、これでも 10 年以上前のバージョンです。GH-7620
- 同梱テーマを [release-20250915-154825-b4500fc](https://github.com/mbadolato/iTerm2-Color-Schemes/releases/tag/release-20250915-154825-b4500fc) に更新しました。テーマは上流で管理されているため、テーマの名前や色が変わっている場合があります。**1.1.3 で使えていたテーマが 1.2 への更新後に使えなくなった場合は、リンク先のリリースでテーマ名を確認してください。**
- フォント機能 `dlig` は既定で無効になりました。これにより、以前は表示されていた合字が表示されなくなる場合があります。仕様上、この機能はもともと「任意の合字」で、必要なときだけ有効にするものです。より一般的な `calt`（文脈依存の合字）は引き続き既定で有効です。必要に応じて `font-features` 設定で再度有効にできます。GH-8164

### 非推奨 {/* #deprecations */}

以下の項目は非推奨です。現在は互換レイヤーによって引き続き使えますが、そのままにしておくと将来のリリースで動かなくなる可能性があります。

- `adw-toolbar-style` は `gtk-toolbar-style` に名前が変わりました。
- `gtk-tabs-location=hidden` は `window-show-tab-bar=never` に置き換わりました。
- `selection-invert-fg-bg` は `selection-foreground=cell-background` と `selection-background=cell-foreground` に置き換わりました。GH-5219
- `cursor-invert-fg-bg` は `cursor-color=cell-foreground` と `cursor-text=cell-background` に置き換わりました。GH-5219

非推奨の項目を削除する時期は決まっていませんが、今後の不具合を避けるため、早めに新しい設定へ移行することをおすすめします。

<Note>
  上記の非推奨の設定は、警告を表示せずに引き続き動作します。今後のリリースでは、設定に関する警告を GUI に表示する予定です。
</Note>

### パッケージメンテナー向けの変更 {/* #changes-for-package-maintainers */}

- 多くのソース tarball と同様に、一部のファイルを前処理した状態でソース tarball を生成するようになりました（たとえば、パーサーの `.y` を `.c` に変換するなど）。Ghostty では Blueprint の `ui` ファイルを `xml` ファイルに変換し、翻訳や GTK リソースファイルも前処理します。これにより、新しいビルドツールを利用できない古いプラットフォームでも Ghostty をビルドできます。**パッケージ作成には、Git のチェックアウトではなくソース tarball を使用してください。`PACKAGING.md` にこの情報を追記しました。** GH-6800

- GLFW のアプリランタイムを削除しました。正式にサポートしたことはなく、開発とテストにのみ使用していました。`PACKAGING.md` でも GLFW 版をパッケージ化しないよう注意を促していました。開発にもテストにも不要になったため、削除しました。GH-7815

- tip リリースは、同じコミットからすでに公開された tip リリースを上書きしなくなりました。これにより、リリース後もチェックサムが変わりません。tip パッケージを提供するパッケージ作成者にとっては、セキュリティやツールとの互換性の向上につながります。tip リリースは以前から署名されています。GH-8549

#### Flatpak と Snap の最新状況 {/* #flatpaksnap-update */}

Ghostty 1.2 には、Flatpak と Snap 向けのビルド設定が含まれるようになりました。CI でコミットごとにテストし、これらの形式で配布しても Ghostty が動作するよう努めています。ただし、Flatpak や Snap のパッケージはまだ公式には提供・保守していません。

これは大きな進展です。Ghostty 1.1.x はパッチなしでは Flatpak や Snap のパッケージとしてまったく動作せず、公式プロジェクトもこれらのパッケージの保守を保証していませんでした。まだ公式配布には至りませんが、今は少なくともこれらの形式でビルドし、テストしています。

公式配布への主な課題は、**保守を引き受けるメンテナーの確保**とリリースの自動化です。現在の Ghostty メンテナーには Snap 版や Flatpak 版を普段使いしている人がおらず、長期的にこれらのパッケージを保守できるという確信がありません。Ghostty の Flatpak または Snap パッケージの保守にご協力いただける方は、Discord に参加し、`#packaging` でご連絡ください。

## ロードマップ {/* #roadmap */}

Ghostty 1.3 でも、Ghostty を [「既存の中で最良のターミナルエミュレーター」](https://mitchellh.com/writing/ghostty-1-0-reflection) にするという方針を継続し、ほかの主要なターミナルエミュレーターと同等の機能を揃えるために、まだ欠けている主要な機能を追加します。具体的には、少なくともスクロールバック検索とスクロールバーを 1.3 で提供する予定です。[^1]

Ghostty 1.3 は主にデスクトップアプリの機能に注力します（スクロールバック検索とスクロールバーもその一部です）。Ghostty の中核のターミナルエミュレーション機能は、すでに豊富で安定していることが実証されています。ただし、他の開発者が最近公開した実験的なプロトコルを取り入れるなど、VT の機能も引き続き拡充する予定です。

よくある要望についてですが、**Windows 対応**と**独立したライブラリとしての libghostty** は、Ghostty 1.3 では予定していません。長期ロードマップには引き続き含まれますが、まずは既存のプラットフォームとデスクトップアプリに注力します。

### 3 月・9 月のリリースサイクルに移行 {/* #moving-to-a-marchseptember-release-cycle */}

Ghostty のメジャーリリースとマイナーリリースは 6 か月ごとに行うようになります。次回のマイナーリリース（1.3.0）は 2026 年 3 月を予定しています。3 月と 9 月のリリースサイクルは、主要な Linux ディストリビューションの多くや macOS のリリース時期と合わせやすくなります。パッチリリース（1.2.1 など）は、必要に応じて随時行います。

現代のアプリとしては比較的長いリリースサイクルですが、開発チームが影響の大きい機能に注力し、tip リリースで十分に安定させる時間を確保できます。パッケージ作成者も頻繁に新版をパッケージ化せずに済みます。また、主要な OS のリリース時期と合わせることで、新しい OS で十分に動作するメジャーリリースを提供できます。

より頻繁な更新を希望する場合は、macOS では [`tip` リリースチャンネル](/docs/config/reference#auto-update-channel) を使い、Linux ではこまめに [ソースからビルド](/docs/install/release-notes/1-1-0#roadmap) することをおすすめします。ナイトリービルドには数千人のユーザーがいます（テストへのご協力ありがとうございます）。メンテナー全員で tip リリースの安定性を保つよう努めています。1.1 から 1.2 までの開発期間を通じて、tip リリースが普段使いできないほど壊れたことは、私の記憶にはありません。
