Ghostty 1.1.0 には、**84 人の貢献者**による **564 件のコミット**にわたる、**1 か月分の成果**が含まれています。このリリースでは引き続き、最初の 1.0 リリースへのフィードバックをもとに、重大なバグの修正と使い勝手の改善に注力しています。

## セキュリティ {/* #security */}

## 主な変更点 {/* #highlights */}

### Linux のサーバー側ウィンドウ装飾（SSD） {/* #server-side-decorations-(ssd)-on-linux */}

PR:
[#4630](https://github.com/ghostty-org/ghostty/pull/4630),
[#4723](https://github.com/ghostty-org/ghostty/pull/4723),
[#5124](https://github.com/ghostty-org/ghostty/pull/5124)

特に Linux では、ウィンドウ装飾のスタイルや挙動が環境によって大きく異なります。以前の Ghostty は常にクライアント側ウィンドウ装飾（CSD）を使っていたため、見た目も使い勝手も「GNOME」アプリに偏っていました。特に KDE Plasma のような人気のデスクトップ環境では、Ghostty が周囲になじみませんでした。

Linux 版 Ghostty 1.1 は、対応するコンポジター上でサーバー側ウィンドウ装飾（SSD）を使えるようになりました。これにより、より多くのデスクトップ環境で、見た目と使い勝手がネイティブアプリに近づきます。CSD を使いたい場合や、装飾自体が不要な場合は無効にできます。

（左／上: 従来のクライアント側ウィンドウ装飾、右／下: 新しいサーバー側ウィンドウ装飾）

`window-decoration` 設定に新しい値 `auto` が加わりました。コンポジターが SSD に対応していて優先する場合に、SSD を使います。`server` は、利用可能であれば SSD を強制します。`client` はクライアント側ウィンドウ装飾を強制し、`none` は装飾を完全に無効にします。

SSD は Wayland でのみ利用できます。Ghostty は [KDE Server Decoration](https://wayland.app/protocols/kde-server-decoration) プロトコルを使います。この名前ですが、KDE だけでなくほぼすべての主要な Wayland コンポジターが対応しています。X11 では広く対応している SSD 用プロトコルが見つからなかったため、引き続き CSD を使います。

今後の Ghostty でも、利用可能なプロトコルの範囲内で、Linux のさまざまなデスクトップ環境に見た目と使い勝手がなじむよう、できる限り改善していきます。現在は、たとえばネイティブのメニューバーを検討しています。

<Important>
将来の Ghostty では、`gtk-adwaita` オプションを削除し、libadwaita を必須にします。今回の変更に関連するのは、SSD を必要とするユーザーの大多数が、SSD を使うために `gtk-adwaita = false` を設定していたことです（ただし一部の場合にしか動作しませんでした）。新しい SSD 対応により、この回避策は不要になりました。詳しくは [該当する節](#gtk:-forcing-a-dependency-on-libadwaita) を参照してください。
</Important>

### 入力メソッド（IME）の改善 {/* #input-method-editor-(ime)-improvements */}

PR:
[#3567](https://github.com/ghostty-org/ghostty/pull/3567),
[#4332](https://github.com/ghostty-org/ghostty/pull/4332),
[#4539](https://github.com/ghostty-org/ghostty/issues/4539),
[#4854](https://github.com/ghostty-org/ghostty/pull/4854),
[#4933](https://github.com/ghostty-org/ghostty/pull/4933),
[#4999](https://github.com/ghostty-org/ghostty/pull/4999)

macOS と Linux の両方で、CJK（中国語、日本語、韓国語）、デッドキー（アクセント付き文字など）、絵文字、Unicode の 16 進入力など、さまざまな方式で IME をテストし、入力の信頼性と一貫性を大幅に改善しました。

Linux では、X11 と Wayland の両方で `fcitx` と `ibus` をテストしました。それぞれ複数のバージョン（特に LTS ディストリビューションで広く使われているもの）をテストしました。ibus 1.5.29 では、デッドキーの入力が解除されなくなるバグを見つけ、回避策を実装しました。

macOS では特に、日本語入力の AquaSKK と macSKK が追加設定なしで動作することを確認しました。ほかの IME もテストし、問題なく動作することを確認しています。

### 実行可能な場合に限るキーバインド {/* #"performable"-keybindings */}

PR:
[#4328](https://github.com/ghostty-org/ghostty/pull/4328)

キーバインドに新しい `performable:` プレフィックスを使えるようになりました。アクションが実際に実行された場合に限り、キーバインドが入力を消費します。

たとえば、以下のキーバインドでは、コピー可能なテキストがある場合にのみ `ctrl+c` の入力を消費します。なければ `ctrl+c` はシェルに渡されます（通常は割り込みシグナルが発生します）。

```
keybind = performable:ctrl+c=copy_to_clipboard
```

<Note>
すべてのアクションが `performable:` に対応するわけではありません。たとえば `text` や `new_tab` など、多くのアクションは常に実行されます。このプレフィックスが適用されるのは、アクションを実行するかどうかが状況によって変わる場合だけです。
</Note>

### macOS: アルファブレンディングの改善 {/* #macos:-alpha-blending-improvements */}

PR:
[#4913](https://github.com/ghostty-org/ghostty/pull/4913),
[#5401](https://github.com/ghostty-org/ghostty/pull/5401)

アルファブレンディングとは、半透明の前景色を背景色の上に重ねたときの色を求める処理です。文字の輪郭や、Kitty 画像プロトコルで表示する透過部分のある画像に影響します。

以前は sRGB 色空間で色を合成していたため、前景色と背景色がどちらも高彩度で異なる色の場合、文字の輪郭が暗くなっていました。macOS 版 Ghostty 1.1 では、既定で P3 色空間を使ってアルファブレンディングを行います。色域が広がって輪郭の暗さが軽減され、Terminal.app や TextEdit など macOS のネイティブアプリと表示が揃います。

また、この挙動を制御する `alpha-blending` 設定を追加しました。既定値は上述の `native` ですが、ほかに二つの選択肢があります。

- `linear` は線形色空間で合成します。技術的には正しい方法ですが、暗い文字が細く、明るい文字が太く見えるなどの欠点があります。
- `linear-corrected` は `linear` に似ていますが、文字に補正を加えることで、`native` に極めて近い見た目になり、輪郭が暗くなる問題も _まったく_ ありません。

以下で、左から従来のブレンディング、新しい `native`、`linear`、`linear-corrected` を比較できます。違いを正確に見分けるには画像を拡大する必要があるかもしれません。

現時点では macOS でのみ利用できますが、将来は Linux でも使えるよう開発を進めています。

### macOS: クイックターミナルの改善 {/* #macos:-quick-terminal-improvements */}

PR:
[#4049](https://github.com/ghostty-org/ghostty/pull/4049),
[#4501](https://github.com/ghostty-org/ghostty/pull/4501),
[#4999](https://github.com/ghostty-org/ghostty/pull/4999),
[#5361](https://github.com/ghostty-org/ghostty/pull/5361)

クイックターミナルが、ネイティブのフルスクリーンウィンドウ、クイックターミナルを開いたままでの操作スペースの切り替え、IME ウィジェット、左右に配置した Dock などに対応しました。

クイックターミナルを開いたまま macOS の操作スペースを切り替えた場合の挙動を制御する、新しい `quick-terminal-space-behavior` 設定を追加しました。既定ではアクティブな操作スペースに追従します（`move`）。`remain` にすると、最初に開いた操作スペースに留まります。

## ロードマップ {/* #roadmap */}

1.1.0 に間に合わなかったバグをいくつか修正するため、1.1.1 をリリースする予定です。重大な問題やリグレッションが報告されない限り、すぐにリリースする見込みはありません。そのため、すべてのパッケージメンテナーに、できるだけ早く 1.1.0 へ更新することをおすすめします。

次のリリースでは、特定のキーボード配列で起きる問題の解消を引き続き進めるとともに、macOS の `window-step-resize` に関する根本的な問題にも取り組みます。思いがけない貢献があれば、予定していなかった機能が加わるかもしれません（貢献ありがとうございます）。

最初の 1.0 リリース以来、幅広い環境で安定して使える段階に近づいています。開発チームが影響の大きい機能に注力できるよう、近いうちにリリース間隔をさらに延ばし、数か月単位にする見込みです。

### GTK: libadwaita の必須化 {/* #gtk:-forcing-a-dependency-on-libadwaita */}

Ghostty 1.2 から、`gtk-adwaita` オプションを削除し、libadwaita を必須にする予定です。libadwaita はすでに既定で有効なので、明示的に無効にしていない限り影響はありません。

<Important>
**この判断に異論がある方もいらっしゃると思います。** 判断に至った理由と、判断する前にどのような検討を重ねたかを知っていただくために、この節をよくお読みください。それでも懸念があれば、GitHub または Discord でご連絡ください。
</Important>

以前の Ghostty で `gtk-adwaita = false` が主に使われていたのは、`window-decoration = none` と組み合わせて、一部のコンポジターにサーバー側ウィンドウ装飾（SSD）を強制するためでした。すべてのケースで動作するわけではなく、設定が意図した使い方でもありません。たまたま一部のケースで動いていたにすぎません。Ghostty 1.1 で [SSD に正式対応](#server-side-decorations-(ssd)-on-linux) したため、_この回避策は不要になりました_。

`gtk-adwaita = false` のもう一つの用途はテーマの適用です。Ghostty 1.1 では、GTK の要素の見た目をカスタム CSS で簡単に変更できる [`gtk-custom-css` オプション](https://github.com/ghostty-org/ghostty/issues/4200) を追加しました。GTK ウィジェット全体に、CSS の対象として指定しやすいクラス名も導入しました。システム全体の CSS で Ghostty の外観を変えることは以前から可能でしたが、このオプションにより、Ghostty 専用のカスタム CSS を試し、適用しやすくなります。

Ghostty のメンテナーにとって、「従来の GTK」と「libadwaita」の両方のコードパスを保守するのは大きな負担です。GTK と Adwaita のバージョンによる挙動の違いに加え、Ghostty のさまざまな設定（`gtk-` や `adw-` で始まるすべてのオプション）の組み合わせも複雑です。その結果、コストが高く複雑な CI 環境がなければ修正やテストが難しいバグやリグレッションがいくつも発生しています。

Ghostty 1.1 が SSD に対応し、`gtk-adwaita = false` の主な用途がなくなったため、今が変更に適した時期だと考えています。これにより、今後の Ghostty は安定性が増し、保守しやすくなり、より多くの機能を提供できると考えています。libadwaita の機能を全面的に活用できるためです。

この判断に確信を持てるよう、GNOME を使っていない Ghostty ユーザーや、Ghostty の見た目や使い勝手に不満を持つ Ghostty 非ユーザー（ブロガー、配信者、YouTuber）にも直接意見を聞きました。全員が変更に賛同し、判断の理由と利点を理解したうえで、SSD への正式対応によって主な懸念が解消されると認めてくれました。

この変更について強いご意見がある場合は、Discord または GitHub でご連絡ください。その際、この変更がどのように影響するのか、具体的な用途や状況を添えてください。理由のない「気に入らない」だけでは参考になりません。フィードバックは歓迎しており、いただいた内容は慎重に検討します。ありがとうございます。
